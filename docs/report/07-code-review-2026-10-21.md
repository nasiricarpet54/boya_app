## یافتهٔ ۱ — باگ timezone در تبدیل تاریخ جلالی (رفع شد)

**شدت:** متوسط — باگ پنهانِ محیط‌محور.

`JalaliDateService.toGregorian()` و `getWeekStart()` از `newDate()` در
`date-fns-jalali` استفاده می‌کردند. این تابع نیمه‌شب **محلی** می‌سازد، پس لحظهٔ
حاصله با timezone ماشین جابه‌جا می‌شد: روی CI و production (UTC) یک لحظه، روی
لپ‌تاپ تهران (UTC+3:30) ۳ ساعت و ۳۰ دقیقه جلوتر. ۲ تست از ۸۰ در ایران قرمز و در
CI سبز بودند.

`getWeekStart()` بدتر بود: `newDate()` (محلی) + `setUTCDate()` (UTC) روی همان شیء —
بسته به timezone می‌توانست یک روز جلو/عقب بیفتد.

**راه‌حل:** تابع کمکی `jalaliDayToUtcMidnight()` که با همان `parse()` موجود، لحظهٔ
نیمه‌شب UTC را می‌سازد. جزئیات تصمیم: `DECISIONS.md` → ADR-012.

**اثر بر محصول:** هیچ‌کدام از این دو متد production caller ندارند (فقط تست)، پس
هیچ API عمومی جابه‌جا نشد.

## یافتهٔ ۲ — `TypeOrmModule.forRoot` تکراری در تست integration (رفع شد)

`backend/test/integration/location.integration-spec.ts` دو بار `TypeOrmModule.forRoot({...})`
داشت که باعث تداخل اتصال و خطای ماژول‌سازی Nest می‌شد. یکی حذف شد.

## یافتهٔ ۳ — نام پویا در شش migration (رفع شد — سرور production را گرفتار کرده بود)

**شدت:** بالا — استقرار production را متوقف کرد.

شش migration نامشان را در زمان اجرا می‌ساختند:

```ts
name = 'ExclusionConstraint' + String(Date.now()); // Fallback name
```

نام در هر boot متفاوت است، پس TypeORM هرگز آن‌ها را با ledger تطبیق نمی‌دهد و **هر
بار استقرار دوباره اجراشان می‌کند**. سرور production برای هر کدام ۱۲ ردیف در ledger
داشت — یعنی ۱۱ بار تکرار.

عوارض:

1. استقرار production با خطای `42P07: relation "schedule_blocks" already exists` متوقف شد.
2. `CreateScheduleBlocks` به جدول `salons` ارجاع می‌داد که **اصلاً وجود ندارد**
   (یک سالن، همان رکورد `tenants` است) و از `CREATE TABLE` بدون `IF NOT EXISTS` استفاده
   می‌کرد، پس روی دیتابیسی که جدول از قبل داشت شکست می‌خورد.
3. قید `no_double_booking` هرگز ساخته نشد، چون گارد migration فقط `contype='x'` را
   می‌بیند و قید معادل `no_overlapping_bookings` از قبل روی `bookings` بوده.

**راه‌حل:** نام هر شش migration ثابت شد و دقیقاً برابر با ردیف موجود در ledger تولید
شد (تا TypeORM آن‌ها را «اجراشده» بشناسد). `CreateScheduleBlocks` هم `IF NOT EXISTS` و
`DROP POLICY IF EXISTS` گرفت و FK آن به `tenants` اصلاح شد.

**نتیجه:** ledger production از ۱۱۶ به ۱۱۷ ردیف رسید و اجرای مجدد
`migration:run` پیام «No migrations are pending» می‌دهد. جزئیات: `DECISIONS.md` → ADR-013.

## نکات باز (بدون تغییر — خارج از دامنهٔ این کار)

- **تست integration اجرا نشد.** `npm run test:e2e` به Postgres و Redis واقعی نیاز
  دارد. روی این ماشین سرویسی بالا نبود. CI این را پوشش می‌دهد.
- **`TZ` در `backend/Dockerfile` و CI صریح تنظیم نشده** و به UTC می‌افتد. تصمیم
  ADR-012 به آن وابسته نیست، ولی صریح‌کردنش (`ENV TZ=UTC`) یک خط است و رفتار را
  در برابر تغییر پیش‌فرض image پایدار می‌کند.
- **`toGregorian`/`getWeekStart` هیچ caller تولیدی ندارند.** یا باید به یک API واقعی
  وصل شوند (مثلاً فیلتر «رزروهای یک روز») یا باید به‌عنوان dead code حذف شوند.

## قرارداد تبدیل تاریخ (تأییدشده)

«یک روز جلالی» = یک بازهٔ ۲۴ ساعتهٔ ثابت در UTC. نه نیمه‌شب تهران، نه نیمه‌شب محلی.
دلیل: نتیجه باید روی CI، لپ‌تاپ توسعه‌دهنده و production **یکسان** باشد. اگر بعداً
«نیمه‌شب به وقت تهران» لازم شد، باید `Asia/Tehran` صریح اضافه شود.
